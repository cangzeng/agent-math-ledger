# Revision proposal：阴性判定与可行性判定的两处代理信号污染

状态：**提案，未生效**。写入日期 2026-11-27。待维护者采纳后才并入 `RULES.md`。

## 缘起

2026-11-27 的一轮纠错暴露出两次同形状的失效，一次来自方案评估，一次来自仓库查找。两次都不是算力不足，也不是拼写错，而是**用一个廉价的代理信号替代了它声称要证明的东西**，且两次的静态检查都全绿。

## 条款 A：内部闭环冒充可行性

**症状**：框架自己检查自己、自己给自己出收据、自己宣布自洽，然后把"内部无矛盾"读作"外部可行"。内部闭环只能证明实现与规格一致，不能证明规格对应真实需求、真实人口或真实能力。

**本项目的对应实例**：`FALSIFICATION.md` v0.1 把"仓库公开可访问"当成验证开始。零曝光下的零提交，只证明没人知道，不证明没人要。v0.2 用曝光前置条件 G1/G2/G3 修补；v0.3 进一步把 G2 改成按目标渠道协议交工件，并只数收据级闭合。

**判据**：任何"可行"结论必须指出它在框架之外的对应物；若证据全部来自框架内部，结论强度只能到"内部一致"，不得升级为"可行"。

## 条款 B：搜索为空冒充不存在（A 的姊妹条款）

**症状**：以某次检索无结果，判定对象不存在。中间只要检索词本身可能受损，否定结论就无效。

**本项目的对应实例（事故，事实级错误）**：我在评估 B 方案前提时，用了汇编文档里的转录名 `agent-conversation-challenge`，检索为空，于是报告"查无此仓"，并据此推翻 B 方案。用户独立复核指出真实仓库是 `arc-open-governance/agent-consequence-challenge`（`consequence` 非 `conversation`）——仓库真实存在，Issue #1 自述协议 "How a task is claimed: post the artifact on this issue"。阴性判定不成立。

**根因**：不是名字拼错，而是**阴性判定没有认证义务**。检索词来自二手汇编，未回查原始出处；也没有直接探测目标 URL——一次直接探测就足以戳穿转录错误。搜索结果为空是廉价代理信号，存在性是另一回事。

**判据**：输出否定结论（不存在 / 没有 / 查无 / 不支持）之前，须完成三步：

1. **回查原始出处**，核对检索词是否转录正确，尤其当词来自摘要、汇编或转述时；
2. **直接探测目标**，用候选 URL / 规范名 / 权威来源做一次正路径命中，而不是只看搜索结果列表；
3. **不得用单一代理信号**替代存在性结论。任一步未完成，只能输出"未在本通道检出"，不得输出"不存在"。

## 共同形状

两条是同一条元原则的两个切面：**把结论的强度与适用范围锁在证据实际覆盖的范围内，不外推。**

- A 管"框架内部证据不得推出框架外部可行性"；
- B 管"单一检索通道的阴性不得推出存在性否定"。

它们与既有的"判断四原则·证据效力边界"同源：②证据必须与论点同向（零曝光证据与需求论点不同向；转录错误的检索词与存在性论点不同向），④单一通道不得否决整条路线。

## 机器闸要求（不写闸等于没写）

按本项目既有教训：文档里的约束不是约束，只有写盘前会自动 FAIL 的断言才是。因此本提案若被采纳，须同时落地机器闸，并做注毒反测：

- **A 闸**：任何对外发布的可行性结论，若其证据列表全部指向框架内部产物（自己的 README、自己的规则书、自己的检查器），写盘前 FAIL。
- **B 闸**：任何否定性结论须携带 `origin_check` 与 `direct_probe` 两个字段及其实测值；缺失则 FAIL。
- **注毒反测**：把旧的错误检索词 `agent-conversation-challenge` 和"内部闭环即证明可行"的论证注回样本，闸必须 FAIL；若注毒后仍 PASS，视为假绿，该闸不得上线。

## 边界

本提案只收紧判定义务，不禁止搜索、不禁止内部自检、不要求穷尽证明。它不承诺提高判断准确率——没有测量装置，不能声称量化效果。它的作用是让上述两次已发生的具体失效在复发时能被机器拦下。
